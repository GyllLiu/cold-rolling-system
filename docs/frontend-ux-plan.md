# 冷二联前端界面与交互优化方案

> 基线：本地提交 `724b3fe`（工作区干净）。本文只讨论前端展示与交互，不改动 `app/lib/route-planner.ts` 的算法、`backend/app/model_artifacts/` 的模型参数、`/api/*` 接口、SQLite / OSS 存储和 CSV 字段。
>
> 目标用户与任务不变：
>
> | 页面 | 使用者 | 任务 |
> | --- | --- | --- |
> | `/` 道次推荐 | 工艺工程师、调机人员 | 输入条件，先得到「几道、厚度怎么走、哪里要注意」，再查逐道参数与依据 |
> | `/capture` 拍照记录 | 现场工人 | 拍照 → 保存 → 选道次 → 开始 → 结束，尽量少思考、少点击 |

---

## 0. 摘要

推荐页现在的问题不是「信息不够」，而是**结论、警告、依据散落在不同区块**：道次数在横幅、厚度在路线条、负荷结论在一段文字里、未覆盖原因根本没有渲染。拍照页的问题不是「功能缺失」，而是**照片保存、OCR、人工核对、生产状态四种状态混在两个徽标里**，工人需要自己拼。

本方案的主线只有两句：

1. **推荐页先给答案，再给证据。** 新增一张「结论卡」，只回答三件事：推荐几道、厚度怎么走、有没有需要注意的问题；其余逐道参数、物理校核、选择依据全部下移并分层展开。
2. **拍照页把状态拆开，把操作放到手边。** 照片状态、识别状态、核对状态、生产状态各自独立显示；保存按钮回到照片下方；开始/结束的幂等与重试逻辑原样保留。

不改业务判断，不填示例数值，不动接口和存储。所有新数字都来自现有 `RoutePlan` 字段或现有接口返回值。

## 1. 目标、边界与不变量

### 1.1 设计目标

- 推荐页：打开结果后 **5 秒内**能说出「几道、入口到出口怎么走、第一条要注意什么」。
- 拍照页：照片拍完后，工人 **最多 3 次点击**（保存、选道次、开始）进入上机状态；任何 OCR 异常都不增加必填项。
- 两个页面都做到：手机上不横向滚动、关键按钮不在一屏之外、键盘可完成主流程。

### 1.2 必须保留（硬约束）

- 一个道次 = F1 + F2 完整通过；当前不规划中间退火；不直接控制 PLC。
- 没有数据支撑的参数继续显示「暂不推荐」，**不得为版面填充示例值、占位值或推算值**。
- 拍照页不增加批号/牌号/状态的必填表单，不增加「从相册选择」入口。
- OCR 失败、识别存疑、尚未人工核对，都不能阻止拍照、保存、开始、结束。
- 照片确认保存成功后才能开始；上传期间历史可看，不能用整页遮罩锁住页面。
- 开始 = 上机开始；结束 = 本道全部完成；中途停机不结束。
- 保留上传、开始、结束的重试保护：同一照片 ID、同一开始/结束时间戳、失败后可重试，不产生重复照片或重复生产记录。
- 照片完整显示，`object-fit: contain`，不裁掉随行卡。
- 「已保存」「识别完成」「待核对」「已人工核对」四种状态必须明确区分。
- 本机试用记录与服务器采集记录仍是两套存储，不合并。

### 1.3 非目标

- 不改推荐算法、候选排序、负荷筛选、材料状态映射。
- 不改 `/api/capture/*`、`/api/process-plan`、`/api/recommendations` 的请求/响应结构。
- 不引入组件库、不换构建方式（继续 vinext + Vite + 手写 CSS）。
- 不做账号体系、多语言、暗色模式。

## 3. 三条可选路线与取舍

| 方向 | 做法 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 结论先行 + 渐进展开（推荐） | 结果顶部一张结论卡；方案比较、路线、逐道、校核依次下移；默认只展开结论 | 改动集中在展示层；不打断现有流程；最适合两类用户 | 需要防止摘要与明细数字漂移 | **推荐页采用** |
| B. 全流程向导 | 把「填条件→看方案→导出」拆成步骤页 | 新手友好 | 工程师要反复下一步；结果与输入割裂；移动端更啰嗦 | 不采用 |
| C. 专家仪表盘 | 所有参数首屏平铺、表格化 | 专家查数快 | 现场可读性差；结论被淹没；与「先结论」目标相反 | 不采用 |

拍照页采用 **A + 轻量步骤提示**：保留一屏完成的主操作区，只在顶部加一条非交互的「拍照 → 保存 → 选道次 → 开始 → 结束」进度提示，不做强制向导、不做步骤门禁。

## 4. 推荐页设计

### 4.1 信息架构（调整后）

```
顶部品牌 / 导航 / 服务状态
工艺推演台（计算后收窄）
规则条（一个道次 / 压下顺序 / 张力口径）
┌ 左：本卷条件（sticky） ┐   ┌ 右：结果 ─────────────────────────────┐
│ 牌号 1060/1100/3003    │   │ 1. 结论卡：几道 + 厚度路径 + 需注意     │
│ 来料/目标厚度、宽度    │   │ 2. 方案比较（仅两套方案时）             │
│ 来料状态、目标状态     │   │ 3. 厚度路线（含每道压下率）             │
│ 实时总压下率           │   │ 4. 逐道参数（默认收起依据）             │
│ [计算整道次方案] [清空]│   │ 5. 校核与依据（数据/设备/质量）         │
│ 本机记录 / 导出 CSV    │   │ 6. 退火与状态                           │
└────────────────────────┘   │ 7. 高速数据范围（折叠）                 │
                              └────────────────────────────────────────┘
```

与现状的差异：结论卡置顶；方案比较移到结论之后；负荷/质量从一段文字变成三行状态；`parameterUnavailableReason` 进入结论卡与逐道区；「路线选择依据」「高速数据范围」保持折叠，不抢主视线。

### 4.2 结论卡（新增，推荐页核心）

版式示意（**N / 箭头 / 省略号都是占位，不是示例数值**）：

```
┌──────────────────────────────────────────────────────────────┐
│ 推荐 N 道 · 末道优选                    生成于 --:-- · 规则 -- │
│                                                              │
│ 入口 ──NN.N%──▶ 中间 1 ──NN.N%──▶ … ──NN.N%──▶ 目标 mm      │
│                                                              │
│ [历史覆盖 正常]  [设备负荷 接近上限]  [工艺质量 需复核]      │
│                                                              │
│ 需注意 2 条                                                  │
│  • 第 N 道 F1 保守校核接近力限值，请现场确认                 │
│  • 末道落在复核区，板形需现场确认                            │
│                                                              │
│ [查看逐道参数 ↓]   [对比另一套方案 →]                        │
└──────────────────────────────────────────────────────────────┘
```

内容规则：

1. **道次数**：取 `plan.passCount`；若正在看备选方案，标签写「当前查看」而不是「推荐」，并在旁边保留「推荐方案 N 道」的对照，避免把备选误当推荐。
2. **厚度路径**：取 `plan.passes` 的 `entryThickness → exitThickness`；每段标注该道 `totalReductionPercent`。不额外推算任何厚度。
3. **三条状态**：
   - 历史数据覆盖：`normal / warning / outside_history / unavailable` → 「正常 / 接近历史边界 / 超出历史范围 / 参数未覆盖」。
   - 设备负荷：`within_limits / near_limit / over_limit / not_evaluated` → 「在已确认力限值内 / 接近设备上限 / 超出设备上限 / 未评估」。`not_evaluated` 绝不显示成「正常」。
   - 工艺质量：`provisional_rules_met / review_required` → 「满足暂定规则 / 需现场复核」；旁边固定注明「尚无质量验证」，不做「合格」承诺。
4. **需注意**：由 `plan` 纯派生，最多显示 2 条 + 「还有 N 条」展开。优先级建议：
   1. `parameterRecommendationAvailable === false` → 直接引用 `parameterUnavailableReason`，并补一句「厚度与压下率仍可参考」；
   2. 设备 `over_limit` / `near_limit`，取 `safetyTotal` 最大的一道，写明机架与道次；
   3. 数据 `outside_history` / `warning`，写明受影响道次范围；
   4. 质量 `review_required` 或末道 `finishingBand` 为 `review` / `light`；
   5. 存在 `alternatives` → 这是「信息」不是「警告」：`少一道方案可行，但末道压下更重，需现场复核`；
   6. `anneal.final !== "not_required"` → 成品退火工艺卡提示。
   注意区分「警告（需要现场确认）」与「信息（只是另一种选择）」，不要把所有提示都染成黄色。
5. **CTA**：
   - 「查看逐道参数」用页内锚点 `href="#pass-deck"`（`<a>`，不是新按钮），滚动到逐道区；
   - 「对比另一套方案」同样用锚点跳到方案比较；
   - 不新增「重新计算」按钮，左侧表单仍保留主按钮。
6. **可访问性**：结论卡 `aria-live="polite"`；计算成功后把焦点移到结论卡标题（`tabIndex={-1}`），并保留滚动位置在结果顶部。

### 4.3 方案比较

- 仅在 `original.alternatives?.length > 0` 时出现，放在结论卡之后。
- 从「两张卡片」改成「一张对照表」，列 = 推荐方案 + 各备选；行固定为：道次数、厚度路径、末道特点、设备负荷、数据覆盖。所有值来自 `plan` / `alternative`，不新增计算。
- 主方案列头写「推荐 · 末道优选」，备选写 `alternative.label`（现有数据）；表下注明「负荷只用于超限筛选，不参与排序；少一道不代表更优」。
- 选择方式保留现有按钮 + `aria-pressed`，不引入 `<select>`；切换后结论卡、路线、逐道全部同步，横幅的「推荐/当前查看」文案按 4.2 规则修正。
- 如果备选只有一套（当前业务），表格两列足够；如果未来多于一套，列数自适应并允许横向滚动，不截断文字。

### 4.4 厚度路线

- 保留现有 `RouteRail` 的视觉语言（点位 + 连线 + 成品高亮），增加两处信息：
  1. 相邻点之间标注该道总压下率（`NN.N%`），回答「厚度怎么走」；
  2. 成品点加「目标」标签，首点加「来料」标签，避免只靠序号理解。
- 移动端横向滚动加 `scroll-snap` 与左右渐隐，不把 5–8 个点压成不可读的小字。
- 不在路线条里放张力/辊缝，保持「一条路线」的单一职责。

### 4.5 逐道参数

目标：从「所有字段同时铺开」变成「先看这道怎么设，再看为什么」。

每道卡建议分四层：

1. **头行**：`PASS NN` + `入口 → F1 中间 → F2 出口` + 两个独立徽标：「历史覆盖」「负荷」。现状只有一个 `pass.risk` 徽标，建议把数据覆盖与设备负荷拆开（`pass.assessment` 已含两者）。
2. **一行摘要**：本道压下、F1、F2、中间厚度（保留现状）。
3. **设定值组**：
   - 张力 3 项：开卷 / 机架 / 卷取，主值 `T`，副值 `kN/mm²`（现有 `unitTension`）；标签写全，不只写「张力」。
   - 辊缝 2 项：F1 / F2，单位 mm。
   - 每项只保留「值 + 单位」；`p95Error` 从每块下面移到本道的「计算依据」折叠区，避免 5 个 P95 抢视线。
4. **轧制力**：F1 / F2 各一条「对 1000 T 力限值的进度条」，条上标 `safetyTotal` 与利用率；传动侧/操作侧只作为数字与「固定比例折算，不预测偏载」说明，不再用两条色块暗示偏载预测。
5. **依据折叠**：P95、物理基准、DAT 参考、材料系数、低张力校核、收敛信息全部收进 `<details>`，默认关；需要复核时再展开。

`parameterStatus === "route_only"` 时：

- 整卡保留厚度、F1/F2 压下率、中间厚度；
- 设定值区替换为一块明确的提示：「本规格参数未覆盖：张力、辊缝、轧制力暂不推荐」；
- 原因使用 `plan.parameterUnavailableReason`，不要只写「暂无数据」；
- 不显示「—」占位数值，避免看起来像 0 或已计算。

### 4.6 校核与依据

把现在的一段文字拆成三行状态 + 两块折叠：

```
数据覆盖   正常        12 段历史高速记录 · 支持 3 个日期
设备负荷   接近上限    最大校核 NN% / 1000 T · 仅轧制力与张力
工艺质量   需现场复核  板形、轮胎印、目标状态尚无质量验证
```

- 数据覆盖的「12 段 / 3 个日期」来自 `evidence.routeHistoryCases`、`evidence.routeSupportDates`，没有就不写数字。
- 设备负荷的「最大校核」由各道 `f1Force/f2Force.safetyTotal` 取最大值除以 1000 派生；明确「仅覆盖轧制力与张力，不代表电机、扭矩、板形能力」。
- 质量行固定带「尚无质量验证」，不把 `provisional_rules_met` 写成「合格」。
- 折叠 1「为什么是这条路线」：保留 `selection.explanation`、规则版本、候选数/通过数、厚度分区说明、`parameterAssumptions`；候选淘汰原因可做成紧凑列表。
- 折叠 2「高速数据范围」：保留现有 `EnvelopeCard`，标题继续强调「不是设备上限」。
- 页脚补一行：`规则 V0.7.2 · 模型 V0.6.1 · 生成时间`（来自 `plannerVersion` / `modelVersion` / `createdAt`），方便与 CSV、DAT 对齐。

### 4.7 输入区与反馈

- 主按钮改为 `type="submit"`，保留 `onSubmit`；回车可计算，文案仍是「计算整道次方案」。
- 字段级校验：
  - 空值、≤0、目标 ≥ 来料、宽度越界，错误显示在对应字段下方，`aria-invalid` + `aria-describedby`；
  - 现有 `createRoutePlan` 的报错文案（`来料厚度必须大于0`、`目标厚度必须小于来料厚度`、`产品宽度超出高速数据范围 …`）按关键词映射到字段，不要求改算法；
  - 模型级错误（候选搜索失败等）仍保留在按钮上方的全局错误区。
- 实时派生：在尺寸字段下方显示「总压下率 NN.N%」，仅在两个厚度都合法时显示；这是输入的直接换算，不是模型建议，需标注「按输入尺寸」。
- 「清空」改为「清空尺寸」，因为它保留牌号与状态；或保留文案但在旁边注明「保留牌号/状态」。
- 本机记录条：文案改为「本机记录 N 条 · 仅保存在此浏览器」；导出后给 `aria-live` 提示「已导出 N 条」，导出按钮禁用时说明「暂无可导出的记录」。
- 计算后：桌面滚动到结论卡；移动端见 4.8。不加全屏 loading，计算是同步的，按钮短暂 `aria-busy` 即可。

### 4.8 移动端与响应式

- `≤1120px` 仍单列，但计算后把结果区排到表单之前：给 `.mill-page` 加 `has-result` 类，`.recipe-stage { order: -1 }`；表单保留在下方，结论卡顶部提供「修改条件 ↓」锚点。
- `≤820px` 计算后隐藏装饰性 hero 与规则条（或压缩成一行「一个道次 = F1+F2」），把首屏让给结论卡；输入条件用一行摘要「1060 · 入口→目标 · 宽度」+「修改」。
- `≤560px`：结论卡内状态三行改两列换行；路径横向滚动；逐道卡设定值 2 列；轧制力上下堆叠；力限值进度条保持全宽。
- 所有触控目标 ≥ 44px；数字输入 `inputMode="decimal"` 保留，字号 ≥16px 防 iOS 缩放。

### 4.9 空态、错误与加载

- 空态高度从 570px 降到约 340px，内容改成三步提示：「① 填本卷条件 ② 计算 ③ 先看推荐道次与厚度路线」，并加一句「没有数据支撑的参数会显示『暂不推荐』」。不放任何示例数值。
- 错误：字段错误就近；全局错误给「发生了什么 + 现在能做什么」，例如「当前条件下没有找到可行路线。请检查厚度/宽度，或联系工艺确认规则；这不代表设备一定不能生产」。
- 结果区加载：同步计算通常很快，不伪造骨架；若后续改为动态加载算法，再补骨架与超时提示。

### 4.10 可访问性

- 合金按钮加 `aria-pressed`，外层 `role="group"` 或保留 `fieldset/legend`。
- 结果容器 `aria-live="polite"`，计算后焦点到结论标题；不要整页重排导致读屏重复朗读。
- 所有状态「颜色 + 文字」双编码；红色/黄色不作为唯一信息。
- `<details>/<summary>` 保持原生键盘行为；表格比较用 `<table>` + `<caption>` 或语义化列表，不用纯 div 模拟。
- 字号底线：推荐页元信息 ≥11px，正文 ≥12px，关键数值 ≥16px；现状 7–9px 的标签统一上调。

## 5. 拍照页设计

### 5.1 状态模型：四个维度分开

现状把「照片保存 / OCR / 核对 / 生产」压成一个顶部徽标 + 一个 OCR 徽标。建议拆成四个维度，集中显示但互不覆盖：

| 维度 | 状态与文案 | 数据来源 |
| --- | --- | --- |
| 照片 | 未拍照 / 待保存 / 上传中 NN% / 已保存 / 保存未确认·可重试 | `staged`、`photo`、`uploadProgress`、`attemptedUpload` |
| 识别 | 识别未启用 / 等待识别 / 正在识别 / **识别完成 · 未核对** / **待核对 · 识别存疑** / 识别失败 · 不影响采集 | `ocr_status` |
| 核对 | 未核对 / **已人工核对** | `reviewed_at` |
| 生产 | 准备上机 / 可以开始 / 本道进行中 / 正在确认结束 / 本道已完成 | `active`、`busy`、`notice` |

关键规则：

- 「已保存」只说明照片已落库，**不暗示识别完成**。
- 「识别完成 · 未核对」对应 `succeeded`；「待核对 · 识别存疑」对应 `needs_review`；「已人工核对」对应 `reviewed_at`。三者互斥且并列，历史卡与详情页使用同一套文案。
- 「识别失败 · 不影响采集」必须保留「不影响采集」这半句，避免工人以为要重拍。
- 顶部生产状态只显示生产/上传，不再承担 OCR 文案；这样「本道进行中」不会因为 OCR 失败而变色或消失。
- 建议新增 `app/capture/capture-status.ts`，集中导出上述映射；页面、历史、详情都从这里取文案，避免四五处硬编码再次漂移。

### 5.2 主操作区布局

保持宽屏左右分栏（左照片、右控制），只移动「保存」：

```
┌ 左：照片（3:4，完整显示，不裁切） ─────────┐  ┌ 右：控制 ──────────────────┐
│                                            │  │ 当前道次  1  2  3  4  5     │
│           [照片 / 空态插画]                │  │                            │
│                                            │  │ [ 开始 ]      [ 结束 ]      │
│ [ 拍照 / 重拍随行卡 ]                      │  │  上机时按     本道完成时按  │
│ [ 保存照片 / 重试保存 / 上传进度 ]         │  │                            │
│ 照片：已保存                               │  │ 开始 --:-- · 已进行 --:--  │
│ 识别：识别完成 · 未核对                    │  │                            │
│ 核对：未核对                               │  │ 识别 / 核对状态（紧凑）     │
└────────────────────────────────────────────┘  └────────────────────────────┘
```

- 左栏：照片 → 拍照/重拍 → 保存/重试/进度 → 三行状态。保存是照片流程的下一步，必须贴着照片。
- 右栏：道次 → 开始/结束 → 开始时间与已进行时长 → OCR/核对紧凑状态 → 反馈/错误。
- 上传进度条只在左栏出现，**不覆盖右栏和历史**；历史仍然可以滚动查看。
- 未保存时，「开始」保持禁用，旁边给一句「照片确认保存后才能开始」，而不是等点击后报错。
- 已保存时，保存按钮消失，改为绿色「照片已保存」状态；重拍按钮保留，点击仍走现有「新照片保存成功后才替换旧照片」的逻辑。
- 未选道次时，「开始」禁用并提示「先选第 1–5 道」；不把 OCR 状态放进禁用条件。

### 5.3 主流程规范

| 步骤 | 触发条件 | 界面 | 禁用/保护 | 文案 |
| --- | --- | --- | --- | --- |
| 拍照 | 无进行中记录 | 相机全屏层；关闭后回到主区 | 已开始时禁用重拍 | 「将随行卡完整放入画面」 |
| 预览 | 拍照/系统相机返回 | 全屏预览，完整 contain | 上传中不可重拍 | 「检查照片是否清晰、四角是否完整」 |
| 保存 | `staged` 存在且非上传中 | 左栏主按钮 | 上传中禁用；开始禁用 | 「保存照片」/「重试保存」 |
| 选道次 | 未开始 | 1–5 大按钮 | 进行中锁定 | 「当前道次」 |
| 开始 | 已加载 + 照片已确认 + 已选道次 + 非忙碌 | 右栏绿色大按钮 | 缺一不可；OCR 不参与 | 「开始 · 上机时按下」 |
| 进行中 | `active` 存在 | 道次锁定，显示计时 | 重拍/选道次/开始禁用 | 「本道进行中 · 中途停机不用按结束」 |
| 结束 | `active` 存在 | 右栏红色大按钮 | 忙碌禁用；重试复用同一时间戳 | 「结束 · 本道全部完成时按下」 |

**结束的防误触（建议，需产品确认）：** 保留一个按钮，首次点击进入 4 秒确认态（按钮文案变为「再按一次确认本道完成」），第二次点击才提交；超时自动还原。相比弹窗，它不遮挡页面、不增加按钮数量，也不影响重试逻辑。若现场反馈「太慢」，可改为长按 800ms 提交。

### 5.4 上传与重试（只改 UI，不改协议）

- 继续使用 `uploadPhoto` 的同 ID、同字节重试；45 秒超时；`onprogress` 到 100% 时只显示「照片已发送，等待服务器确认…」，**不能**提前显示「已保存」。
- `attemptedUpload` 的现有分支保留：
  - 400/401/403/404/409/413/422：服务端明确拒绝，允许重拍/重新保存；
  - 0/5xx/超时：照片可能已落库，禁止重拍，只能「重试保存」；这是防止重复照片的关键。
- 进度区文案分两段：
  - 传输中：「正在上传 NN% · 尚未确认保存，暂不能开始。可以继续查看下方历史。」
  - 等待确认：「照片已发送，等待服务器确认… 请勿关闭页面。」
- 失败文案：「保存未确认。照片仍在本页，点『重试保存』会使用同一张照片 ID，不会新增一张照片。」
- 上传期间不出现全屏遮罩；历史、详情、日期筛选都可操作。
- 不新增取消上传按钮（避免「取消了但服务端已落库」的新歧义）；如确需取消，只能隐藏进度并保留重试，语义要写清。

### 5.5 进行中与结束

- 增加只读计时：`开始时间 HH:mm:ss（北京时间）` + `已进行 HH:mm:ss`，每秒本地刷新；不请求服务端，不改变 `started_at`。
- 进行中把道次按钮显示为锁定态（现有 disabled 保留），并显示「第 N 道」；若无道次标注，继续显示现有提示。
- 结束成功后：提示「第 N 道已完成 · 用时 MM:SS」，清空照片/道次（现有行为），并提示「下一道请先拍照并保存」。
- 结束失败：保留 `pendingEnd`，按钮可重试；界面明确「结束时间尚未确认，记录仍在进行中」，避免工人以为已结束而离开。
- 开始失败但服务端可能已建记录：保留现有 `refresh()` 兜底；界面显示「正在确认开始结果…」，刷新后若已有进行中记录则直接进入进行中态。

### 5.6 历史

- 默认仍是北京时间当天、时间倒序、每页 30 条；日期筛选与「显示已被重拍替换的旧照片」保留。
- 卡片信息分三层：
  1. 时间 + 道次（「第 N 道」用加粗，未标注则写「未选道次」）；
  2. 两个徽标：识别状态 + 核对状态（不再用 reviewed 覆盖 OCR）；
  3. 生产状态与时长：「已完成 · 13:20–13:52（32 分钟）」/「进行中 · 已 12 分钟」/「尚未开始」/「已被重拍替换」。
- 缩略图继续 `PhotoFrame` contain，不裁切；固定宽高避免列表跳动。
- 卡片点击区域保留整卡可点，但补 `aria-label`（「查看 13:20 第 3 道照片与识别结果」），内部文本不再被读成一整段；如要更规范，可改为 `<article>` + 覆盖式按钮 + 文本同级，视觉不变。
- 详情弹层：
  - 左图右信息，图片完整显示；
  - 顶部四维状态（照片/识别/核对/生产），而不是单个徽标；
  - 人工核对入口文案改「核对 / 更正三项信息（可选）」，旁边注明「不核对不影响记录、开始和结束」；
  - 保留原图链接、旋转、重新识别、替换说明、识别原文；
  - 焦点陷阱 + Esc 关闭 + 关闭后焦点回到触发卡片；背景滚动锁定。
- 空态：「今天还没有拍照记录。保存照片后会自动出现在这里。」
- 加载态：2–3 张骨架卡，减少布局跳动（尊重 `prefers-reduced-motion`）。
- 轮询：仅在存在 `queued/processing` 时 3 秒轮询；终态停止；页面隐藏时暂停，`visibilitychange` 恢复时立即刷新一次。减少弱网请求，不改接口。

### 5.7 相机与预览

- 相机层打开时聚焦「拍照」按钮；Esc 关闭；关闭后焦点回到「拍照/重拍」。
- 增加非裁切取景提示：四角框 + 「四角完整、文字可读」；**采集仍用完整视频帧**，不用取景框裁切。
- 权限失败：显示「无法使用相机」+「重新授权」+「用系统相机拍摄」（触发现有隐藏 `capture` input）；不出现「从相册选择」。
- 旋转：保留相机实时旋转 90°、预览旋转、历史旋转；预览旋转只改展示方向，不改原图（现有行为）。
- 预览主按钮是「保存照片」，次按钮「重拍」「旋转」「关闭」；保存后立即回到主区并显示进度，不阻塞。
- 预览/相机层的按钮均为条件渲染，不影响服务端渲染的按钮数量（见第 8 节）。

### 5.8 移动端与可访问性

- `≤760px` 单列：照片（3:4）→ 拍照/重拍 → 保存/进度 → 道次 → 开始/结束 → 计时 → OCR → 历史。
- `≤560px`：道次 5 个按钮保持一行，字号 `clamp(14px, 4vw, 16px)`；开始/结束高度从 144px 降到约 120px，但 ≥56px 触控；安全区 `env(safe-area-inset-bottom)` 保留。
- 状态不只靠颜色：文字 + 形状/图标；黄色「待核对」与绿色「已人工核对」在灰度下也能区分。
- 所有全屏层：`role="dialog"` + `aria-modal` + 标题 `aria-labelledby` + 焦点陷阱 + Esc + 焦点返回。
- 上传进度用 `<progress>` + `aria-live="polite"`；不要每秒朗读，只在阶段变化（开始/100%/成功/失败）播报。

### 5.9 明确不做

- 不加批号/牌号/状态输入框到采集主流程。
- 不加「从相册选择」按钮。
- 不因为 OCR 失败/存疑/未核对而禁用开始或结束。
- 不用全屏遮罩锁住上传中的页面。
- 不改 `uploadPhoto` 的请求头、ID、超时、重试语义。
- 不为了填满卡片使用 `object-fit: cover`。

### 6.3 组件建议

## 10. 度量

上线后建议看四类指标（不需要埋点平台，先用现有日志/人工抽检）：

- **推荐页**：从进入到算出结果的时长；5 秒问答抽检正确率；非法输入一次通过率；移动端结果到达率（是否滚动到结果）。
- **拍照页**：拍照→保存→开始的点击次数与耗时；上传重试成功率；开始/结束重复提交拦截次数；OCR 失败/待核对状态下仍完成采集的比例（应接近 100%，用于证明「不阻断」）。
- **数据质量**：重复照片数、重复生产记录数（目标 0）；未核对记录占比（只观察，不强制）；人工核对耗时。
- **性能**：首屏 JS 体积、LCP、INP；历史轮询请求数（改成终态停止后应明显下降）。

## 11. 风险与取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 摘要与明细漂移 | 结论卡另算一套数 | 所有值从同一个 `plan` 派生；`plan-summary` 单测逐项对照 |
| 警告过多 | 每条都提示会变成「狼来了」 | 最多 2 条 + 展开；区分「警告」与「信息」；按优先级排序 |
| 移动端隐藏表单 | 用户找不到修改入口 | 结论卡固定「修改条件」锚点；表单值不丢 |
| 保存按钮移位 | 工人肌肉记忆 | 只移动位置不改文案/颜色；上线首周在工位贴一张新流程示意 |
| 结束二次确认变慢 | 多一次点击 | 4 秒确认态/长按二选一；先小范围试用再定 |
| 字号整体上调 | 版面变长 | 优先保证关键数值与按钮；元信息用 11–12px，不追大 |
| 状态文案改动 | 与历史记录/培训材料不一致 | 用 `capture-status.ts` 单一来源；旧数据按 `ocr_status`/`reviewed_at` 映射，不做数据迁移 |
| 测试按钮计数 | 新增常驻按钮会失败 | 优先不加；必须加时同步改测试并说明 |
